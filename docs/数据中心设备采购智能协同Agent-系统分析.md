# 一、文档目的

本文档用于说明：

1. 整个系统最终应该具备哪些可正常运行的功能。
2. 不同用户可以使用哪些功能。
3. 每项功能的完整处理流程是什么。
4. Agent、原有采购后端、知识库和业务工具之间如何配合。
5. 系统在正常、异常和权限受限情况下应该如何响应。
6. 项目完成后应达到什么验收标准。

本文档关注“系统最终应该怎样工作”，不展开具体代码实现。

---

# 二、系统整体定位

本系统是在原有采购业务系统基础上增加的智能协同层。

原有采购系统继续负责：

- 用户身份和角色。
- 楼宇权限。
- 采购申请。
- 审批流转。
- 采购执行。
- 供应商和黑名单。
- 入库。
- 业务数据保存。
- 正式写入和操作日志。

Agent 系统负责：

- 理解用户自然语言。
- 判断用户想查询什么。
- 检索采购制度和流程文档。
- 调用采购、产品、供应商和统计工具。
- 组合多个查询结果。
- 生成有依据的解释、对比和风险摘要。
- 保存连续查询的上下文。
- 检查最终回答是否有编造、遗漏或越权。

系统不让 Agent 代替人工审批，也不让 Agent 直接决定最终采购结果。

## 2.1 交付形态和平台边界

- 第一版以 Web 页面作为主要且必须完成的入口。
- 用户可以在网页中完成采购业务操作、智能问答、复杂查询、风险分析和人工确认。
- 开发环境使用现有 TEST 身份切换机制。
- 正式 Web 环境使用服务端登录 Session，并由 BFF 或服务端网关生成后端身份签名。
- 浏览器不得保存身份网关密钥，也不得自行声明角色和楼宇权限。
- 飞书属于后续可选入口，通过适配层调用同一 Agent 服务。
- 未完成飞书接入不影响系统完成判定。

# 三、系统最终组成

完整系统由以下部分组成：

```text
用户入口
├─ Web 登录与采购工作台
├─ Web 智能对话页面
├─ 采购单详情页
├─ 审批页面
├─ 知识库管理页面
└─ Agent 执行记录页面

Agent 智能层
├─ Router Agent
├─ Knowledge Agent
├─ Analysis Agent
├─ Review Agent
├─ RAG 知识检索
├─ 任务规划与工具调用
├─ Memory 与任务状态
└─ Human-in-the-loop

业务工具层
├─ 采购数据 MCP
├─ 产品数据 MCP
├─ 供应商数据 MCP
└─ 统计分析 MCP

业务与数据层
├─ 原采购后端
├─ MySQL
├─ Redis
├─ 向量数据库
└─ 采购制度与历史案例文档

工程保障层
├─ 权限控制
├─ Trace 与日志
├─ 自动评测
├─ 超时、重试和降级
└─ Docker 部署
```

# 四、系统用户角色

## 4.1 需求人

需求人可以使用：

- 采购制度和流程问答。
- 某类设备字段要求查询。
- 自己采购单的状态和问题解释。
- 历史采购品牌和价格查询。
- 自然语言预填采购表单。
- 查询自己有权限查看的采购记录。

需求人不能：

- 查看无权限楼宇的采购明细。
- 查看不允许展示的供应商敏感字段。
- 使用审批功能。
- 让 Agent 自动替自己提交正式采购单。

---

## 4.2 楼长

楼长可以使用：

- 本楼宇采购记录查询。
- 待审批采购单风险摘要。
- 重复申请、价格和数量异常调查。
- 供应商风险查询。
- 历史相似申请查询。
- 审批意见草稿生成。
- 本楼宇相关制度和业务问答。

楼长不能：

- 查看其他楼宇的受限采购详情。
- 让 Agent 自动通过或驳回。
- 绕过原有审批流程。

---

## 4.3 采购员

采购员可以使用：

- 跨楼宇采购数据查询。
- 历史价格和品牌统计。
- 多约束候选产品分析。
- 供应商履约、延期和黑名单查询。
- 采购风险调查。
- 分析报告草稿生成。

采购员不能：

- 让 Agent 自动作出最终供应商选择。
- 让 Agent 自动完成采购执行。
- 让 Agent 绕过业务校验写入正式数据。

---

## 4.4 仓库管理员

仓库管理员可以使用：

- 待入库采购单查询。
- 入库流程问答。
- 历史入库情况查询。
- 入库异常说明。

仓库管理员不能：

- 查看超出权限的采购和供应商数据。
- 让 Agent 自动确认入库结果。

---

## 4.5 系统管理员

系统管理员可以使用：

- 采购知识文档管理。
- 文档版本管理。
- Skill 配置管理。
- Agent Trace 查看。
- 评测结果查看。
- 模型和工具运行状态查看。

系统管理员不直接改变采购审批结果。

# 五、系统最终应正确运行的功能

# 5.1 用户身份与权限识别

## 功能说明

用户进入系统后，系统应能正确识别：

- 用户身份。
- 用户角色。
- 所属楼宇。
- 可查看的数据范围。
- 可调用的功能范围。

## 正常结果

- 开发环境可以使用 TEST 用户切换进行联调。
- 正式 Web 环境由服务端 Session 标识用户，浏览器不直接生成后端签名。
- 用户只能看到自己有权限的数据。
- Agent 只调用当前角色允许的工具。
- 知识库只返回当前用户可查看的文档。
- 任何写入操作都要再次经过后端权限校验。

## 异常结果

如果用户请求越权数据，系统应明确提示：

> 当前账号没有权限查看该楼宇或该采购单的数据。

系统不能因为用户在对话中要求“忽略权限”而返回数据。

---

# 5.2 智能对话入口

## 功能说明

用户可以通过自然语言提出采购相关问题。

系统应支持：

- 单轮问题。
- 连续追问。
- 同一句话中包含多个任务。
- 当前页面上下文，例如当前采购单编号。
- 普通文字、表格、风险摘要和引用结果展示。

## 正常结果

用户输入后，系统显示：

1. 当前正在处理。
2. 必要时显示查询步骤。
3. 返回最终答案。
4. 展示来源、筛选条件和数据范围。
5. 保存本次会话上下文。

## 异常结果

如果系统暂时无法处理，应说明具体原因，而不是只返回“请求失败”。

例如：

- “供应商数据服务暂时不可用。”
- “当前只能完成价格分析，无法完成供应商履约分析。”
- “没有找到足够的制度依据，无法确认该规则。”

---

# 5.3 采购知识问答

## 功能说明

系统应能回答来自采购制度和业务文档的问题。

包括：

- 某类设备需要填写哪些字段。
- 黑名单持续时间规则。
- 各角色职责。
- 采购流程。
- 审批和入库规则。
- 内部采购规范。
- 系统操作说明。

## 正常结果

回答应包含：

- 直接答案。
- 文档来源。
- 文档版本或生效时间。
- 相关章节。
- 如果存在多个版本，说明版本差异。

## 正确运行标准

- 回答必须来自知识库。
- 不得用普通常识补充内部制度。
- 检索不到依据时，明确说明无法确认。
- 过期文档不能作为默认依据。
- 用户无权查看的制度文档不能被引用。

---

# 5.4 业务数据与规则混合问答

## 功能说明

系统应能回答同时需要“业务数据”和“制度规则”的问题。

例如：

- 为什么当前申请不能提交。
- 为什么采购单还停在当前状态。
- 当前流程下一步由谁处理。
- 某项审核意见对应哪条制度。
- 当前供应商是否受黑名单规则限制。

## 正常结果

系统应：

1. 查询当前采购单的实时数据。
2. 检索相关制度或流程规则。
3. 对照实际数据与规则。
4. 给出具体解释。
5. 分别标明数据来源和文档来源。

## 示例结果

> 当前申请缺少设备型号和期望到货时间，因此暂时不能提交。  
> 依据：《服务器设备采购字段要求》V2.1，第 3.2 节。  
> 当前申请编号：PR-2026-0012。

---

# 5.5 自然语言复杂查询

## 功能说明

系统应支持用户直接使用自然语言组合多个查询条件。

可支持的条件包括：

- 时间范围。
- 楼宇。
- 设备类别。
- 品牌。
- 型号。
- 供应商。
- 金额范围。
- 采购状态。
- 审核次数。
- 黑名单。
- 延期记录。
- 分组方式。
- 排序方式。
- 聚合方式。

## 示例

> 查询过去半年一号楼和二号楼采购的服务器硬盘，排除黑名单供应商，只看单价超过 3000 元的，再比较不同品牌的平均价格。

## 正常结果

系统应返回：

- 系统理解出的查询条件。
- 数据表格。
- 品牌或供应商对比。
- 统计结果。
- 使用的时间范围和统计口径。
- 数据不足或条件冲突说明。
- 简洁的自然语言总结。

## 正确运行标准

- 系统理解的条件与用户原意一致。
- 查询结果与数据库直接查询结果一致。
- 不遗漏排除条件。
- 不执行任意 SQL。
- 用户无权限的数据不会进入结果。

---

# 5.6 连续追问和上下文继承

## 功能说明

系统应能理解用户对上一轮查询的补充。

例如：

```text
用户：比较 A 和 B 两个品牌过去一年的采购情况。
系统：返回两个品牌的价格和供应商对比。

用户：再排除有延期记录的供应商。
系统：保留过去一年、A 品牌、B 品牌等条件，只新增延期过滤条件。
```

## 系统应记住

- 上一轮时间范围。
- 楼宇。
- 设备。
- 品牌。
- 供应商。
- 排除条件。
- 统计方式。
- 上一轮结果摘要。

## 正常结果

- 用户不需要重新描述全部条件。
- 新条件覆盖旧条件时，以用户最新表达为准。
- 指代不清时，系统只进行必要澄清。
- 新任务开始后，旧任务条件不会错误带入。

---

# 5.7 多约束候选方案分析

## 功能说明

系统应能处理同时包含多个约束的候选方案分析。

例如：

> 预算 5 万元，优先历史上采购过的品牌，需要兼容现有设备，同时排除黑名单和有多次延期记录的供应商。

## 系统应执行

1. 提取预算、品牌、兼容性和供应商风险条件。
2. 区分硬约束和偏好条件。
3. 查询产品白名单和规格。
4. 查询历史采购。
5. 查询供应商和黑名单。
6. 查询历史价格。
7. 筛选候选项。
8. 解释每个候选项满足和不满足的条件。

## 正常结果

每个候选方案应包含：

- 产品或型号。
- 历史采购情况。
- 历史价格。
- 供应商情况。
- 满足的条件。
- 不满足或未知的条件。
- 数据来源。

## 正确运行标准

- 候选产品必须来自真实数据。
- 不得编造兼容性。
- 没有可靠兼容性数据时必须明确说明。
- 系统只能给候选方案，不能声称唯一最优。
- 最终选择由采购员决定。

---

# 5.8 后端风险检查

## 功能说明

系统应在审批前执行确定性风险检查。

第一版至少支持：

- 短期重复申请。
- 当前价格高于历史统计值。
- 数量明显高于历史范围。
- 当前供应商在有效黑名单中。
- 当前供应商存在延期记录。
- 存在长期未入库记录。
- 存在相似采购申请。
- 同类采购长期集中在同一供应商。

## 正常结果

后端输出结构化风险结果，包括：

- 风险类型。
- 风险等级。
- 命中事实。
- 相关统计值。
- 相关记录编号。
- 判断时间范围。
- 使用的阈值。

## 正确运行标准

- 风险数字由代码和数据库计算。
- 同样的数据应得到稳定一致的结果。
- Agent 不负责凭语言直接判断这些风险。

---

# 5.9 审批辅助与异常调查

## 功能说明

系统应在后端发现风险后，由 Agent 继续补充调查和解释。

## 系统应执行

1. 读取采购单。
2. 读取后端风险检查结果。
3. 判断需要补查哪些数据。
4. 查询历史价格。
5. 查询相似采购。
6. 查询供应商履约和延期。
7. 查询黑名单。
8. 检索相关制度。
9. 生成结构化风险摘要。
10. 交给 Review Agent 审查。

## 正常结果

每条风险摘要应包含：

- 风险类型。
- 风险等级。
- 事实依据。
- 数据来源。
- 适用规则。
- 可能原因。
- 信息是否完整。
- 需要人工核实的内容。

## 正确运行标准

- 每一条风险都能追溯到真实数据或文档。
- 无法确认的内容必须标记为“信息不足”。
- Agent 不得直接给出“通过”或“驳回”结论。
- 楼长仍然自行完成审批。

---

# 5.10 历史相似案例查询

## 功能说明

系统应能根据当前采购单或用户问题，查找相似历史案例。

相似条件可以包括：

- 设备类别。
- 品牌和型号。
- 数量。
- 金额。
- 楼宇。
- 供应商。
- 驳回原因。
- 风险类型。
- 最终处理结果。

## 正常结果

系统应展示：

- 相似案例编号。
- 相似原因。
- 当时的审核意见。
- 当时的处理方式。
- 最终结果。
- 与当前申请的区别。

## 正确运行标准

- 案例必须来自真实历史记录或明确构造的测试案例。
- Agent 不得虚构案例。
- 案例只是参考，不能自动套用审批结果。

---

# 5.11 审批意见和分析报告草稿

## 功能说明

系统可以根据风险摘要生成：

- 通过意见草稿。
- 驳回意见草稿。
- 补充材料请求草稿。
- 采购分析报告草稿。

## 正常流程

```text
Agent 生成草稿
→ 用户查看
→ 用户修改
→ 用户确认
→ 后端再次检查权限
→ 保存到正式业务系统
```

## 正确运行标准

- 未经确认不得写入。
- 用户可以修改或拒绝草稿。
- 写入需要防止重复提交。
- 保存后记录操作人、时间和内容。

---

# 5.12 自然语言表单预填

## 功能说明

用户可以先用一句话描述采购需求，系统自动预填表单。

例如：

> 一号楼需要采购 10 块 8TB 服务器硬盘，预算 4 万元。

系统可以预填：

- 楼宇。
- 设备名称。
- 数量。
- 容量。
- 预算。

## 正常流程

```text
用户输入自然语言
→ 系统提取字段
→ 展示完整采购表单
→ 用户一次性补充和修改
→ 后端校验
→ 用户确认提交
```

## 正确运行标准

- 不使用 Agent 一项一项追问固定字段。
- 无法确定的字段保持为空。
- 用户必须看到和确认完整表单。
- 正式校验由后端完成。

---

# 5.13 采购知识库管理

## 功能说明

系统管理员应能管理 Agent 使用的文档。

支持：

- 上传文档。
- 设置文档名称和类型。
- 设置版本。
- 设置生效时间。
- 设置适用角色。
- 设置适用设备。
- 设置权限范围。
- 标记过期。
- 重新建立索引。
- 查看文档切片和引用效果。

## 正常结果

新文档完成处理后，可以被检索。

旧版本可以保留，但不能默认替代新版本。

## 异常结果

- 文档解析失败时显示失败原因。
- 文档没有完成索引前不能标记为可用。
- 重复版本需要提示管理员。

---

# 5.14 Skills 管理

## 功能说明

系统应能按任务动态加载不同规则。

包括：

- Knowledge Skill。
- Query Skill。
- Recommendation Skill。
- Risk Skill。
- Review Skill。

## 正常结果

- 不同任务加载对应 Skill。
- 本次请求使用的 Skill 版本被记录。
- 更新 Skill 后，后续请求使用新版本。
- 权限不能仅靠 Skill 控制，仍由后端验证。

---

# 5.15 Agent 执行记录

## 功能说明

系统应记录每次 Agent 请求的完整过程。

至少记录：

- 用户问题。
- 用户角色。
- 路由结果。
- 子任务。
- 加载的 Skill。
- 查询计划。
- RAG 检索片段。
- MCP 工具调用。
- 工具参数和结果。
- 中间状态。
- Review 结果。
- 最终回答。
- 耗时。
- Token 和费用。
- 错误和重试。
- 用户反馈。

## 正常结果

管理员可以按 Trace ID 查看完整时间线。

---

# 5.16 自动评测

## 功能说明

系统应能使用固定测试集评测 Agent 效果。

评测范围：

- 路由是否正确。
- 复合任务是否拆分正确。
- RAG 是否召回正确文档。
- 工具是否选对。
- 参数是否提取正确。
- 复杂查询结果是否正确。
- 风险摘要是否有证据。
- 是否出现越权和编造。
- 连续追问是否正确保留上下文。
- 端到端任务是否完成。

## 正常结果

系统能够输出：

- 单项得分。
- 总体得分。
- 失败样例。
- 与上一版本的变化。
- 回归测试结果。

---

# 5.17 容错、恢复和降级

## 功能说明

系统应能处理模型、知识库和业务工具异常。

## 应支持

- 模型超时重试。
- 主模型失败切换备用模型。
- MCP 工具超时。
- 工具连续失败熔断。
- 部分工具成功、部分失败。
- RAG 不可用时降级。
- 工作流中断后恢复。
- 用户确认后继续执行。
- 最大步骤数和最大循环次数。

## 正常降级示例

供应商服务不可用时：

> 当前无法获得供应商延期和履约信息。以下结果仅包含历史价格、采购数量和重复申请分析。

系统不得在缺少数据时编造完整风险结论。

# 六、系统统一处理流程

任何 Agent 请求都遵循以下总流程：

```text
1. 用户发起请求
        ↓
2. 系统识别身份、角色和权限
        ↓
3. 创建 Trace ID 和任务状态
        ↓
4. Router 判断任务类型
        ↓
5. 加载对应 Skill
        ↓
6. 选择知识检索、业务查询或混合流程
        ↓
7. 生成结构化计划
        ↓
8. 调用 RAG 和 MCP 工具
        ↓
9. 保存中间结果
        ↓
10. 判断结果是否足够
        ↓
11. 必要时继续查询
        ↓
12. 生成结构化初步结果
        ↓
13. Review Agent 审查
        ↓
14. 审查不通过则补查或重写
        ↓
15. 高风险写入进入人工确认
        ↓
16. 返回最终结果
        ↓
17. 保存 Memory、Trace 和评测数据
```

# 七、核心业务流程

# 7.1 采购知识问答流程

## 前置条件

- 用户已登录。
- 知识库中存在相关文档。
- 用户有权查看对应文档。

## 主流程

1. 用户输入制度或流程问题。
2. Router 判断为知识问答。
3. 系统加载 Knowledge Skill。
4. Knowledge Agent 改写检索问题。
5. 系统按权限过滤文档。
6. 系统执行向量或关键词检索。
7. 系统对结果进行排序和去重。
8. Knowledge Agent 根据检索片段生成回答。
9. Review Agent 检查回答是否忠于文档。
10. 系统返回答案和引用来源。

## 异常流程

- 没有可靠文档：返回“无法从现有制度中确认”。
- 文档版本冲突：展示冲突和版本。
- 文档无权限：返回权限提示。
- 检索服务失败：明确说明知识查询暂不可用。

---

# 7.2 具体采购单解释流程

## 示例

> 为什么这张采购单不能提交？

## 主流程

1. 系统从页面上下文或用户输入中得到采购单编号。
2. Router 判断为混合问题。
3. 采购 MCP 查询采购单详情。
4. 后端返回缺失字段和当前状态。
5. RAG 检索提交规则和设备字段要求。
6. Knowledge Agent 对照两类结果。
7. 生成具体原因。
8. Review Agent 检查字段和规则是否对应。
9. 返回解释和引用。

## 异常流程

- 采购单不存在：提示编号无效。
- 用户无权限：禁止返回采购单内容。
- 规则文档缺失：只返回业务事实，并说明无法确认制度依据。

---

# 7.3 复杂查询流程

## 主流程

1. 用户提出复合查询。
2. Router 判断为复杂查询。
3. 系统提取结构化查询条件。
4. 将条件展示给用户或写入 Trace。
5. Analysis Agent 生成查询计划。
6. MCP Client 调用采购、产品、供应商和统计工具。
7. 可独立的查询并行执行。
8. 系统合并结果。
9. Analysis Agent 判断结果是否足够。
10. 如不足，补充查询。
11. 系统生成表格、统计和文字总结。
12. Review Agent 检查条件是否遗漏。
13. 返回结果并保存任务上下文。

## 异常流程

- 条件冲突：请求用户澄清。
- 数据量过大：限制范围并提示。
- 单个工具失败：返回部分结果和缺失项。
- 查询结果为空：明确说明没有匹配数据。

---

# 7.4 连续追问流程

## 主流程

1. 用户在上一轮查询后追加条件。
2. 系统读取当前会话记忆。
3. 判断用户是在修改条件还是开启新问题。
4. 将新条件合并到当前查询状态。
5. 只执行需要更新的查询步骤。
6. 返回更新后的结果。
7. 保存新的任务状态。

## 异常流程

- 指代不清：询问一次必要澄清。
- 当前任务已过期：提示用户重新说明核心条件。
- 用户明确开启新任务：清空旧任务条件。

---

# 7.5 多约束候选方案流程

## 主流程

1. 用户提出预算、品牌、兼容性和供应商要求。
2. Router 判断为复杂分析。
3. Analysis Agent 区分：
   - 硬约束。
   - 偏好条件。
   - 未知条件。
4. 查询产品白名单和参数。
5. 查询历史采购和价格。
6. 查询供应商和黑名单。
7. 查询履约和延期记录。
8. 后端按硬约束筛选。
9. Agent 根据偏好整理候选方案。
10. Review Agent 检查每个候选是否有来源。
11. 返回候选方案和差异说明。

## 异常流程

- 没有候选项：说明哪些约束导致无结果。
- 缺少兼容性数据：明确标记为“兼容性未确认”。
- 预算不足：展示最接近但超预算的方案，仅作参考。

---

# 7.6 审批风险摘要流程

## 前置条件

- 用户为楼长或采购员。
- 用户有权限查看当前采购单。
- 采购单处于可审核或可分析状态。

## 主流程

1. 用户打开采购单并点击“生成风险摘要”。
2. 后端执行固定风险规则。
3. 系统创建风险调查任务。
4. Analysis Agent 读取风险命中结果。
5. Agent 生成补充调查计划。
6. 并行查询：
   - 历史价格。
   - 相似采购。
   - 供应商黑名单。
   - 供应商延期。
   - 入库异常。
   - 相关制度。
7. Agent 整理事实和可能原因。
8. 生成结构化风险摘要。
9. Review Agent 逐项核对来源。
10. 证据不足的风险被删除或标记为待确认。
11. 系统向楼长展示摘要。
12. 楼长自行进行审批。

## 异常流程

- 某数据源不可用：显示分析范围不完整。
- 无风险命中：显示“未发现当前规则范围内的明显风险”。
- Review 不通过：系统补查或删除无依据内容。
- 任务超时：保存当前状态，可稍后恢复。

---

# 7.7 审批意见草稿流程

## 主流程

1. 楼长查看风险摘要。
2. 楼长选择生成通过、驳回或补充材料意见草稿。
3. Agent 根据当前申请和风险摘要生成草稿。
4. 前端展示草稿。
5. 楼长修改或确认。
6. 后端再次校验权限和状态。
7. 用户确认后保存。
8. 系统记录审计日志。

## 异常流程

- 采购单状态已变化：禁止保存旧草稿。
- 用户无审批权限：禁止写入。
- 重复提交：幂等控制阻止重复写入。

---

# 7.8 知识库更新流程

## 主流程

1. 管理员上传文档。
2. 设置文档类型、版本、生效时间和权限。
3. 系统解析文档。
4. 系统按条款或章节切分。
5. 系统生成索引。
6. 管理员预览切片和检索效果。
7. 管理员发布文档。
8. 后续 Agent 请求可以检索该文档。

## 异常流程

- 文档解析失败：标记失败并显示原因。
- 索引失败：文档不能发布。
- 版本重复：提示管理员确认。
- 文档过期：停止作为默认依据。

---

# 7.9 任务失败恢复流程

## 主流程

1. Agent 执行过程中保存 Checkpoint。
2. 某个模型或工具调用失败。
3. 系统按照规则重试。
4. 连续失败后触发降级或熔断。
5. 系统保留已完成步骤。
6. 服务恢复后从检查点继续。
7. 返回最终或部分结果。

## 正确运行标准

- 不重复执行已经成功的写入。
- 不因为局部失败丢失全部任务。
- 用户可以看见失败位置和已完成范围。

# 十、系统异常处理要求

## 10.1 模型异常

- 超时后进行有限次数重试。
- 主模型不可用时切换备用模型。
- 结构化输出失败时重新生成。
- 多次失败后返回明确错误。

## 10.2 MCP 工具异常

- 工具超时后重试。
- 连续失败触发熔断。
- 返回部分结果时说明缺少的数据。
- 不使用模型猜测工具结果。

## 10.3 RAG 异常

- 检索不到内容时不编造制度。
- 文档冲突时显示冲突。
- 向量库不可用时说明知识问答不可用。

## 10.4 权限异常

- 越权请求立即阻止。
- 不把越权数据传给大模型。
- 记录权限拦截日志。

## 10.5 任务异常

- 达到最大步骤数时停止。
- 达到最大循环次数时停止。
- 用户可以主动取消长任务。
- 已完成步骤写入 Checkpoint。

# 十一、非功能要求

## 11.1 正确性

- 业务数字与数据库结果一致。
- 制度回答与知识库原文一致。
- 查询条件不能被遗漏。
- 风险结论必须有来源。

## 11.2 可解释性

- 用户可以查看结论来源。
- 用户可以查看使用的查询条件。
- 管理员可以查看 Agent 执行步骤。

## 11.3 安全性

- 权限由后端控制。
- 查询默认只读。
- 写入必须人工确认。
- 重要操作有审计记录。

## 11.4 稳定性

- 单个工具失败不应导致整个系统无提示崩溃。
- 长任务可以恢复。
- 系统有超时、重试和降级机制。

## 11.5 可评测性

- 每个核心模块都有测试集。
- 修改 Prompt、Skill、模型或检索方法后可以回归测试。
- 能比较不同版本效果。

## 11.6 可部署性

- 第一版提供可独立使用的 Web 页面。
- 采购后端和 Agent 服务可以独立启动和重启。
- MCP 第一版可以使用 stdio，不要求独立网络端口。
- 系统可通过 Docker Compose 启动。
- 核心服务有健康检查。
- 配置和密钥与代码分离。

# 十二、系统验收场景

## 12.1 知识问答验收

输入：

> 黑名单持续时间规则是什么？

通过标准：

- 返回正确规则。
- 有文档来源和版本。
- 不引用过期文档。
- 没有依据时不编造。

---

## 12.2 混合问答验收

输入：

> 为什么采购单 PR-001 不能提交？

通过标准：

- 正确查询采购单。
- 正确识别缺失字段。
- 正确检索提交规则。
- 返回具体原因和来源。

---

## 12.3 复杂查询验收

输入：

> 查过去半年一号楼和二号楼采购的服务器硬盘，排除黑名单供应商，只看单价超过 3000 元的，并按品牌统计平均价格。

通过标准：

- 时间、楼宇、设备、金额和排除条件全部正确。
- 统计结果与数据库一致。
- 返回查询条件和统计口径。
- 不返回越权数据。

---

## 12.4 连续追问验收

上一轮查询后输入：

> 再排除有延期记录的供应商。

通过标准：

- 保留上一轮其他条件。
- 只新增延期排除。
- 返回更新后的结果。
- 不要求用户重新说明全部条件。

---

## 12.5 候选方案验收

输入：

> 预算 5 万元，优先历史品牌，排除黑名单和有多次延期的供应商。

通过标准：

- 正确区分硬约束和偏好。
- 候选项全部来自数据库。
- 每个方案有理由和来源。
- 不声称唯一最优。

---

## 12.6 风险摘要验收

选择一张包含价格异常和供应商延期记录的采购单。

通过标准：

- 后端正确命中风险。
- Agent 正确补查证据。
- 每条风险有数据和制度来源。
- 不替楼长做审批决定。

---

## 12.7 Human-in-the-loop 验收

生成驳回意见草稿。

通过标准：

- Agent 只能生成草稿。
- 未经用户确认不能写入。
- 用户可以修改。
- 保存前重新校验权限和状态。
- 重复点击不会重复写入。

---

## 12.8 权限验收

需求人请求查看其他楼宇敏感采购数据。

通过标准：

- 请求被阻止。
- 数据不传入 Agent。
- 返回明确权限提示。
- 记录审计日志。

---

## 12.9 故障验收

模拟供应商 MCP 服务不可用。

通过标准：

- 系统不编造供应商结果。
- 返回其他可完成的分析。
- 明确说明缺失范围。
- Trace 中记录错误和重试过程。

---

## 12.10 恢复验收

在复杂查询执行中断后恢复任务。

通过标准：

- 从最近 Checkpoint 继续。
- 不重复已完成步骤。
- 最终结果完整。
- Trace 保留中断和恢复记录。

---


## 12.11 Web 入口与身份验收

通过标准：

- 用户可以在网页中完成三条核心 Agent 流程。
- 开发环境的 TEST 身份切换可以正确触发后端权限校验。
- 浏览器中不存在身份网关密钥。
- 正式 Web 方案中，签名由服务端 Session/BFF 生成。
- 飞书未接入时，网页版仍能完整运行和验收。

# 十三、系统完成判定

项目可以被认为“完整实现”，至少需要满足以下条件：

1. 用户可以通过网页版使用三条核心主线。
2. 知识问答可以正确引用采购文档。
3. 业务问题可以结合实时数据和制度回答。
4. 复杂查询可以处理跨多个条件的组合问题。
5. 连续追问可以继承上下文。
6. 审批前可以生成有依据的风险摘要。
7. Agent 结论可以追溯到工具结果或文档。
8. Review Agent 能发现部分无依据、遗漏或越权问题。
9. 高风险写入必须经过人工确认。
10. 权限不依赖大模型判断。
11. 工具失败时可以重试、降级或返回部分结果。
12. 复杂任务可以保存状态并恢复。
13. 每次请求都有完整 Trace。
14. 核心功能有固定评测集和回归测试。
15. 整个系统可以通过 Docker Compose 启动并完成端到端演示。
16. 采购后端和 Agent 服务保持独立，任一 Agent 故障不阻断普通采购流程。
17. 飞书接入不是第一版完成条件。

# 十四、最终系统运行效果

系统实现后，用户应该能够完成以下完整过程：

```text
用户打开 Web 系统并登录
→ 系统识别角色和数据权限
→ 用户通过自然语言提出采购问题
→ 系统自动判断问题类型
→ 从制度文档和实时业务数据中获取依据
→ 必要时自动规划并调用多个工具
→ 根据中间结果继续查询
→ 生成表格、候选方案或风险摘要
→ Review Agent 检查来源和边界
→ 用户获得可追溯结果
→ 涉及正式写入时由用户确认
→ 系统保存业务结果、Trace 和评测数据
```

最终形成的不是一个“采购聊天机器人”，而是一套能够连接采购知识、业务数据、统计规则和人工审批流程的智能协同系统。

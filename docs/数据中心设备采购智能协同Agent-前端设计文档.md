## 1. 文档目的

本文档用于明确数据中心设备采购智能协同系统 Web 前端的第一版设计方案，包括：

- 前端技术栈；
- 页面信息架构；
- 不同角色的菜单与权限视图；
- 整体布局与视觉风格；
- 工作台、智能助手、采购申请等核心页面设计；
- 通用列表页和详情页规范；
- Agent 交互、RAG 引用、Tool 结果和 HITL 的页面呈现方式；
- 前端工程目录、API 对接和开发顺序；
- 第一阶段验收标准。

当前阶段仅完成 Web 前端。飞书、钉钉、微信等平台接入不在本阶段范围内，待 Web 端流程验证、联调和测试通过后再单独设计。

### 1.1 V0.2 实现同步

阶段 23 已在 V0.1 信息架构上完成以下增强，本文继续保持“设计文档”属性，不记录逐项开发日志：

- 智能助手使用 Agent SSE Streaming，展示 thinking/analyzing 等业务化处理中状态、正文、Citation、Tool 摘要、确认请求和最终完成/错误事件。
- Assistant Page 和 Context Assistant 均支持 `AbortController` 取消；失败后可重试，页面卸载会终止活动请求。
- HITL 确认卡片覆盖确认、取消、过期和重复处理；正式写入仍由 Backend 状态机执行。
- 采购详情引入 Context Assistant Drawer，通过受控 `ui_context` 传递 `page_type`、`requirement_id` 和可选 `user_draft`；权威事实由 Tool 回查。
- 楼长、采购员、仓管岗位待办使用集中刷新后的 Badge；数量来自真实列表 `total`。
- 供应商选择改为远程名称搜索；楼长供应商风险页使用楼宇范围正式 API。
- ADMIN 使用独立菜单、工作台、员工管理和采购/供应商全局只读页面，不显示普通岗位写入口。
- Backend field error 在前端统一映射为中文业务提示，业务状态、字段和枚举集中中文展示。

## 2. 前端定位

系统前端定位为：

> 现代、简洁、正式的企业级采购智能协同平台。

设计需要同时满足两类场景：

1. **传统采购业务系统**
   - 采购申请；
   - 审批；
   - 采购执行；
   - 入库；
   - 供应商；
   - 采购历史。

2. **Agent 智能协同**
   - 采购知识问答；
   - 实时采购查询；
   - 复杂采购分析；
   - RAG 引用；
   - Tool 查询结果；
   - 多轮会话；
   - 表单预填；
   - 人工确认。

整体不采用传统灰白色后台风格，也不采用黑色科技大屏、赛博风、重渐变或玻璃拟态。

## 3. 技术栈

### 3.1 核心框架

第一版前端采用：

- **React**
- **TypeScript**
- **Vite**
- **React Router**
- **Ant Design**
- **Ant Design X**

其中：

- React + TypeScript 负责整体前端应用；
- Vite 负责开发与构建；
- React Router 负责前端路由；
- Ant Design 负责表单、表格、卡片、弹窗、布局等企业业务组件；
- Ant Design X 负责 Agent 会话、消息气泡、输入框、引用来源等 AI 交互组件。

### 3.2 辅助技术

当前实际使用：

- React Context：开发身份与角色状态；
- Fetch + AbortController：JSON、SSE、超时与取消；
- Ant Design Form：业务表单与字段校验；
- react-markdown：Agent Markdown 回答渲染；
- Ant Design Icons：图标。

Zustand、Axios、React Hook Form、Zod、Lucide React 和 ECharts 当前均未引入；只有出现明确需求时再评估。

第一版不引入 Next.js，不增加 SSR、Server Components 或额外 Node 后端。

## 4. 总体设计原则

### 4.1 正式但不过度复杂

前端应体现企业系统的稳定感和清晰的信息层级，同时避免模板化的“传统后台感”。

核心原则：

- 蓝白色为主；
- 大量留白；
- 信息层级清晰；
- 同类页面使用统一结构；
- Agent 页面可以比普通业务页更有产品感；
- 不为了视觉效果牺牲信息密度和操作效率；
- 不增加无业务意义的数据大屏和虚假 KPI。

### 4.2 业务身份与岗位职责分离

所有角色都拥有普通员工发起采购申请的能力。

因此前端将用户能力分成：

- **我的采购**：用户作为普通员工发起和查看自己的采购申请；
- **岗位工作**：用户基于楼长、采购员、仓管等角色承担的岗位职责；
- **智能助手**：所有角色共享的 Agent 能力。

这样避免采购员、楼长、仓管看到“新建采购申请”时产生角色突兀感。

### 4.3 新建采购申请不占左侧导航

“新建采购申请”是独立页面，但不作为左侧菜单项。

入口来自：

- 工作台的“手动新建采购申请”按钮；
- “我的采购申请”页面右上角的“新建采购申请”按钮。

- 主色：`#1677FF`

### 5.3 页面风格

整体倾向：

> 蓝白、干净、轻量、现代、正式。

工作台欢迎区和 Agent Welcome 区域可以使用非常轻的蓝色渐变，但不作为全站主要视觉效果。

## 8. 工作台设计

工作台是用户登录后的首页，用于回答：

- 我现在有什么需要处理？
- 我的采购申请进展如何？
- 我最常用的入口在哪里？

工作台不做数据大屏。

### 8.1 页面结构

#### A. 欢迎区

显示：

- 用户姓名；
- 当前角色；
- 简短欢迎语。

例如：

```text
您好，张三
欢迎使用数据中心采购智能协同系统
```

#### B. 核心快捷入口

两个主要按钮：

- 手动新建采购申请；
- 智能助手。

#### C. 状态概览

仅展示和当前用户直接相关的少量数据：

- 待我处理；
- 进行中；
- 已完成。

#### D. 我的待办

根据角色动态变化：

- 需求人：草稿、被驳回、需要继续处理的申请；
- 楼长：待审批；
- 采购员：待采购；
- 仓管：待入库。

#### E. 最近采购申请

展示用户最近发起或参与的采购申请，可直接进入详情。

### 8.2 不做的内容

第一版工作台不添加：

- 无意义折线图；
- 饼图；
- 全国地图；
- 虚假采购金额趋势；
- 与当前角色无直接关系的大屏统计。

## 9. 智能助手页面

智能助手是系统核心展示页面，应与普通业务页保持统一视觉语言，但具有更明显的 Agent 产品感。

### 9.1 页面布局

建议采用双栏：

```text
┌──────────────┬────────────────────────────────────┐
│ 历史会话     │ 智能采购助手                       │
│              │                                    │
│ 新建会话     │ 会话内容                           │
│              │                                    │
│ 今天         │ 用户消息                           │
│ 会话 A       │ Agent 回答                         │
│ 会话 B       │ 来源 / Tool / 业务卡片             │
│              │                                    │
│              │ 输入框                             │
└──────────────┴────────────────────────────────────┘
```

### 9.2 Ant Design X 组件

优先使用：

- Conversations；
- Bubble；
- Sender；
- Welcome；
- Prompts；
- Sources；
- Actions。

### 9.3 Agent 回答支持的内容

消息区需预留以下展示能力：

1. 普通文本 / Markdown；
2. RAG 来源引用；
3. Tool 查询状态；
4. Tool 查询结果摘要；
5. 采购申请卡片；
6. 供应商卡片；
7. 分析结果卡片；
8. Loading / Agent 处理中；
9. 错误和重试；
10. HITL 确认卡片。

### 9.4 不展示的内部信息

普通用户页面不直接展示：

- LangGraph；
- Router；
- Planner；
- Model Trace；
- Prompt；
- API Key；
- 内部错误堆栈。

如后续需要调试视图，可以仅在开发环境增加单独的 Debug Panel。

筛选区：

- 关键词搜索；
- 状态；
- 时间；

- Table；
- Pagination；
- Loading；

- 采购单号；

## 12. 采购申请详情

建立统一详情页，所有角色复用同一页面框架，根据权限显示不同内容和操作。

### 12.1 页面内容

包括：

- 当前状态；
- 基本申请信息；
- 设备信息；
- 申请原因；
- 当前处理人；
- 流程进度；
- 审批信息；
- 采购执行信息；
- 入库信息；
- 操作历史。

### 12.2 流程展示

采用步骤或时间线：

```text
申请提交
→ 楼长审批
→ 采购执行
→ 仓库入库
→ 完成
```

驳回和重新提交需在时间线中保留历史记录。

### 12.3 角色操作

根据后端权限动态显示：

- 需求人：修改 / 重新提交；
- 楼长：审核、驳回；
- 采购员：开始采购、选择供应商、提交仓库；
- 仓管：登记入库、完成；
- 其他无权限角色：只读。

前端不自行判定最终业务权限，后端仍是权威来源。

## 18. Agent HITL 前端设计

涉及正式业务状态变更时，Agent 不直接执行。

页面需支持确认卡片。

例如：

```text
智能助手已为你整理采购申请：

设备：……
数量：……
申请原因：……

[确认提交] [继续修改]
```

需要人工确认的动作包括：

- 提交采购申请；
- 审批通过；
- 审批驳回；
- 最终选择供应商；
- 写入采购结果；
- 入库；
- 其他改变正式业务状态的操作。

确认动作仍调用现有后端正式接口，必须继续经过：

- 权限；
- expected_version；
- action_token；
- 状态机；
- 后端校验。

- Agent thinking；
- Retrieving；
- Tool executing；
- Waiting for confirmation；
- Model timeout；
- Retry；
- Deterministic safe fallback。

普通用户不需要看到内部模型错误细节。

## 20. API 对接原则

### 20.1 两类 API

前端主要对接：

```text
Procurement Backend : 8000
Agent Service       : 8100
```

### 20.2 API Client

前端建立：

- `backendClient`
- `agentClient`

统一处理：

- base URL；
- headers；
- timeout；
- error mapping；
- response envelope；
- authentication / identity context。

### 20.3 接口真实性

开发前必须先审计现有后端真实 OpenAPI / API 实现。

原则：

> 页面根据真实接口开发，不根据页面想象新的后端能力。

如果某个页面暂无真实接口：

- 可以保留页面结构；
- Mock 必须集中管理；
- 必须明确标注开发状态；
- 不允许把 Mock 数据伪装成真实业务数据。

## 21. Agent API 适配

当前 Agent 请求结构：

```json
{
  "platform_type": "TEST_PLATFORM",
  "platform_user_id": "test-user-01",
  "message": "用户问题",
  "external_conversation_id": "外部会话标识",
  "external_message_id": "消息幂等标识"
}
```

当前主要响应：

```json
{
  "success": true,
  "trace_id": "...",
  "data": {
    "conversation_id": 93028,
    "route": "KNOWLEDGE | REALTIME_BUSINESS | HYBRID",
    "reply": "...",
    "tool_call_count": 1,
    "evidence_count": 5,
    "knowledge": {},
    "review": {},
    "execution": {
      "trace_events": [],
      "tools": [],
      "errors": [],
      "model_usage": {}
    }
  }
}
```

前端正常展示时主要消费：

- conversation_id；
- reply；
- knowledge / citation；
- tool 结果；
- error；
- HITL 信息。

`execution.trace_events`、`model_usage` 等内部信息默认不直接展示给普通用户。

## 22. 前端权限设计

前端菜单和按钮根据当前用户角色动态展示。

但：

> 前端权限只用于 UI 控制，不能作为正式安全边界。

后端继续负责最终：

- 身份；
- 角色；
- 楼宇范围；
- 数据访问；
- 状态转换；
- 写操作授权。

前端即使隐藏某个按钮，也不能替代后端权限检查。

## 27. 当前冻结决策

截至 V0.2，以下内容作为第一版前端设计与实现基线：

- React + TypeScript + Vite；
- Ant Design + Ant Design X；
- 蓝白色现代企业系统；
- Sidebar + Header + Content 统一布局；
- 所有角色共享工作台、智能助手、我的采购；
- 岗位工作按角色扩展；
- 新建采购申请不占 Sidebar；
- 工作台突出待办、进行中、已完成和两个核心快捷入口；
- 智能助手采用独立完整页面；
- Agent 主对话与上下文助手均使用 SSE，并支持取消、重试和明确结束状态；
- 采购详情可打开 Context Assistant，但页面草稿不作为后端事实；
- ADMIN 使用独立信息架构，采购与供应商全局访问保持只读；
- 普通用户不暴露 Agent 内部技术 Trace；
- 前端优先接真实 Backend / Agent API；
- Web 完成后再考虑外部办公平台接入。

# 数据中心设备采购智能协同 Agent 需求分析

> 版本：V2.2
> 更新日期：2026-08-14

> 实现口径：四个 Agent 名称表示同一 Agent Service 内的 Router、Knowledge、Analysis、Review 逻辑角色，不是四个独立部署服务。独立动态 Skills 系统不再作为第一版必须目标；当前规则由结构化 Role Prompt、Tool Contract、Graph 节点、知识文档和 Backend 确定性规则承载。

## 一、项目背景

当前采购系统已经能够完成采购申请、楼长审核、采购执行、入库、供应商管理和黑名单管理等基础流程。

权限判断、状态流转、字段校验、金额计算、审批操作和数据保存都有明确规则，应继续由普通后端系统负责，不交给 Agent 决定。

但在实际采购过程中，仍然存在三类普通表单和固定查询页面不容易解决的问题：

1. 采购制度、角色职责、设备字段要求和流程规则分散在不同文档中，用户难以快速找到准确答案。
2. 用户可能提出跨楼宇、时间、设备、品牌、供应商和金额等多个条件的复杂问题，固定查询页面难以覆盖所有组合。
3. 楼长审批时需要同时查看重复申请、历史价格、供应商风险、异常数量和相关制度，人工逐项查询成本较高。

因此，本项目在原有采购业务系统上增加一个智能协同层。

Agent 不替代采购系统，也不替代人工审批，而是负责理解问题、检索知识、调用业务工具、组合多个查询结果，并生成有依据的回答或分析结果。

---

## 二、项目定位

项目名称暂定为：

## 数据中心设备采购智能协同 Agent

项目定位：

> 在现有采购业务系统基础上，增加采购知识与业务问答、采购复杂查询与分析、审批辅助与异常调查三类智能能力。

三个方向之间不是互相独立的，而是逐层递进：

```text
采购知识与业务问答
        ↓
提供制度、流程和规则依据

采购复杂查询与分析
        ↓
提供跨数据源查询和统计能力

审批辅助与异常调查
        ↓
综合规则、数据和历史案例，形成完整业务分析
```

其中，审批辅助与异常调查是最完整的展示场景；知识问答和复杂查询是它的基础能力。

### 交付形态与平台策略

第一版以**网页版**作为主要交付形态，用户通过 Web 页面完成采购业务操作、智能问答、复杂查询、风险分析和人工确认。

平台策略如下：

- P0 阶段优先复用现有开发体验页面，并增加“智能协同”页面。
- Agent 服务与采购业务后端保持平台无关，不绑定飞书消息格式或卡片协议。
- 开发环境继续使用现有 TEST 身份切换机制验证角色和楼宇权限。
- 正式 Web 化时，由服务端登录层或 BFF 保存 Session，并在服务端完成采购后端身份签名。
- 浏览器不得保存或生成采购后端的身份网关密钥。
- 飞书仅作为 P2 可选接入渠道，通过独立适配层复用同一 Agent API 和采购后端。
- 是否完成飞书接入不影响第一版项目验收。

## 三、项目目标

### 1. 业务目标

- 让用户通过自然语言快速查询采购制度、流程和业务状态。
- 支持普通筛选页面难以覆盖的复合条件查询。
- 帮助楼长和采购员快速获得审批重点和风险依据。
- 减少用户在多个页面和文档之间反复查找信息的成本。
- 提高历史采购、供应商、审核记录和制度文档的利用率。

### 2. Agent 技术目标

项目需要形成一条完整、可控制、可恢复、可评测的 Agent 链路，实际覆盖：

- Agent 路由和复合任务拆分。
- 有状态工作流。
- RAG 知识检索。
- MCP 业务工具接入。
- 任务规划和多工具调用。
- 会话记忆和任务状态。
- Skills 动态业务规则。
- 结构化输出。
- Human-in-the-loop。
- Review Agent 证据审查。
- Trace、监控和自动评测。
- 超时、重试、降级和失败恢复。
- 权限控制和安全边界。

## 四、系统分工与边界

### 1. 原有后端系统负责

- 用户身份验证和最终业务权限校验。
- 角色和楼宇权限判断。
- 采购申请创建与保存。
- 采购状态流转。
- 审批通过和驳回。
- 必填字段校验。
- 金额和预算计算。
- 黑名单是否生效。
- 历史价格统计。
- 重复申请检查。
- 数量异常检查。
- 正式修改、提交和入库。
- 操作日志记录。

### 2. Web 入口与服务端身份层负责

- 提供网页版采购业务页面和智能协同页面。
- 在开发环境下使用 TEST 身份完成角色切换和联调。
- 在正式 Web 环境下维护登录 Session。
- 在服务端生成采购后端所需的身份签名。
- 将普通采购请求发送给采购后端，将智能请求发送给 Agent 服务。
- 不把身份网关密钥暴露给浏览器。

### 3. Agent 负责

- 理解用户自然语言问题。
- 判断问题属于知识问答、复杂查询还是审批分析。
- 识别一个问题中包含的多个子任务。
- 从采购知识库检索制度和流程依据。
- 调用采购、产品、供应商和统计分析工具。
- 将复杂问题拆成多个查询步骤。
- 根据中间结果决定是否继续查询。
- 组合多个数据源的结果。
- 生成带依据的回答、查询分析或风险摘要。
- 保存连续查询中的上下文和当前任务状态。
- 检查最终回答是否存在编造、遗漏或越权。

### 4. Agent 不负责

- 自动审批。
- 自动驳回。
- 自动选择最终供应商。
- 自动修改正式业务数据。
- 自动提交正式采购单。
- 自动决定采购结果。
- 直接执行任意 SQL。
- 使用模型判断用户权限。

## 五、主要用户角色

### 1. 需求人

主要使用：

- 采购知识问答。
- 当前申请无法提交的原因解释。
- 采购流程和下一处理人查询。
- 采购历史和常用品牌查询。
- 自然语言预填采购表单。

### 2. 楼长

主要使用：

- 待审批申请风险摘要。
- 重复采购和异常数量调查。
- 历史价格和相似申请查询。
- 供应商风险查询。
- 审批意见草稿生成。

### 3. 采购员

主要使用：

- 跨楼宇、设备、品牌和供应商的复杂查询。
- 多约束候选方案分析。
- 历史价格和供应商履约对比。
- 黑名单、延期和入库异常调查。

### 4. 仓库管理员

主要使用：

- 入库流程和职责问答。
- 历史入库记录查询。
- 采购内容与入库异常说明。

# 六、核心方向一：采购知识与业务问答

## 1. 目标

帮助用户快速理解采购制度、业务流程、角色职责和具体采购单的处理情况。

## 2. 典型问题

- 某类设备采购需要填写哪些字段。
- 为什么当前申请不能提交。
- 黑名单持续时间规则是什么。
- 各角色分别负责什么。
- 当前采购流程下一步由谁处理。
- 当前采购单为什么停留在这个状态。
- 某类设备历史上通常采购哪些品牌。
- 内部制度和采购规范中有哪些要求。

## 3. 问题类型

### 纯文档知识问题

主要从知识库中检索：

- 采购制度。
- 角色职责。
- 设备字段要求。
- 黑名单规则。
- 采购流程说明。
- 系统使用说明。

### 具体业务数据问题

需要查询业务系统：

- 当前申请缺少哪些字段。
- 当前申请为什么不能提交。
- 当前采购单下一步由谁处理。
- 某类设备历史上采购过哪些品牌。

### 文档规则与业务数据结合的问题

例如：

> 为什么这张服务器硬盘采购单不能提交？

系统需要先查询当前申请的缺失字段，再检索服务器硬盘的字段要求和提交规则，最后结合两部分信息解释原因。

## 4. 完整链路

```text
用户提问
→ 判断是文档问题、业务数据问题或混合问题
→ 加载知识问答 Skill
→ 检索 RAG 知识库或调用业务工具
→ 必要时同时使用两者
→ 生成带来源的回答
→ Review Agent 检查引用和事实
→ 返回结果
```

## 5. 关键要求

- 制度类回答必须标明文档来源和版本。
- 涉及具体采购单时必须查询实时业务数据。
- 文档与业务数据冲突时，明确说明冲突，不自行选择答案。
- 检索不到可靠依据时明确表示无法确认。
- 不使用通用常识补充内部制度。

# 七、核心方向二：采购复杂查询与分析

## 1. 目标

支持用户直接用自然语言提出跨多个条件、多个数据源的采购查询和分析问题。

## 2. 典型问题

- 查询过去半年一号楼和二号楼采购的服务器硬盘，排除黑名单供应商，只看单价超过 3000 元的，再比较不同品牌的平均价格。
- 查询过去一年采购次数最多的三类设备，并统计主要品牌。
- 查询被楼长驳回两次以上，最终又成功采购的申请。
- 查询哪些供应商给不同楼宇提供过同类设备，并且价格差距较大。
- 比较 A、B 两个品牌在不同楼宇的历史采购价格和供应商履约情况。
- 查找当前预算范围内、兼容现有设备、历史上采购过且供应商风险较低的候选产品。

## 3. 多约束候选方案

智能推荐不单独作为一个独立核心方向，而是复杂查询与分析的一种结果形式。

简单排序和固定筛选由后端完成。Agent 主要处理同时包含多个条件的分析问题，例如：

> 预算 5 万元，优先以前采购过的品牌，需要兼容现有设备，同时排除黑名单供应商，给出几个候选方案。

Agent 负责：

- 理解复合条件。
- 区分硬约束和偏好条件。
- 生成查询计划。
- 调用产品、采购、供应商和统计工具。
- 根据结果调整后续查询。
- 解释每个候选方案满足和不满足的条件。

准确判断仍由后端工具完成：

- 是否超预算。
- 是否兼容。
- 是否在白名单。
- 是否属于有效黑名单。
- 历史价格统计。
- 供应商履约统计。

## 4. 任务规划要求

Analysis Agent 面对复杂问题时，需要先输出结构化计划，计划至少包含：

- 查询目标。
- 已识别条件。
- 缺失或冲突条件。
- 计划调用的工具。
- 各步骤之间的依赖关系。
- 预计输出形式。

计划可以根据中间结果动态调整，但必须受以下限制：

- 最大执行步骤数。
- 最大工具调用次数。
- 总超时时间。
- 最大循环次数。
- Token 和费用预算。
- 明确的终止条件。

## 5. 完整链路

```text
用户提出复杂问题
→ 提取时间、楼宇、设备、供应商、金额等条件
→ 识别单任务或复合任务
→ 创建任务状态和 Checkpoint
→ 加载分析 Skill
→ 生成结构化查询计划
→ 通过 MCP 调用多个业务工具
→ 可并行的查询并行执行
→ 根据中间结果补充或调整步骤
→ 组合结果
→ 生成表格、对比或候选方案
→ Review Agent 检查条件、证据和结论
→ 返回结果
→ 保存任务记忆和 Trace
```

## 6. 连续追问

```text
用户：比较 A 和 B 两个品牌过去一年的采购情况。
Agent：返回价格、采购次数和主要供应商对比。
用户：再排除有延期记录的供应商。
Agent：保留上一轮的设备、时间和品牌条件，继续查询并更新结果。
```

记忆用于保存当前分析任务，不用于逐项填写固定表单。

## 7. 关键要求

- Agent 不直接执行任意 SQL。
- Agent 只输出受控查询条件或调用受控工具。
- 每个查询结果必须说明筛选条件。
- 数据不足或条件冲突时必须明确说明。
- 候选产品和供应商必须来自工具返回结果。
- 不使用“唯一最优”或“绝对推荐”等表述。

# 八、核心方向三：审批辅助与异常调查

## 1. 目标

帮助楼长或采购员在审批前快速了解采购申请中的重要风险，并调查风险可能产生的原因。

## 2. 后端先负责发现异常

精确风险判断由后端规则和数据库查询完成，例如：

- 是否存在短期重复申请。
- 当前价格是否明显高于历史价格。
- 当前供应商是否在有效黑名单中。
- 供应商是否存在延期交付记录。
- 采购数量是否明显异常。
- 是否存在相似历史申请。
- 是否长期集中选择同一家供应商。
- 采购完成后是否长期未入库。

Agent 不凭文字或感觉直接判断这些风险。

## 3. Agent 负责继续调查和解释

Agent 读取后端风险检查结果后，可以继续：

- 查询同类设备历史价格。
- 查询相同楼宇近期采购情况。
- 查询供应商历史合作和延期记录。
- 查询类似审批案例。
- 检索对应采购制度和规则。
- 判断当前数据是否足以支持结论。
- 区分事实、规则命中、可能原因和信息不足。
- 生成简洁、带来源的审批风险摘要。

## 4. 风险摘要结构

每一项风险至少包含：

- 风险类型。
- 风险等级。
- 事实描述。
- 数据来源。
- 适用规则。
- 可能原因。
- 仍需人工确认的内容。

## 5. 完整链路

```text
楼长打开待审批采购单
→ 后端执行固定风险检查
→ 创建审批调查任务
→ Agent 读取申请和风险结果
→ 生成补充调查计划
→ 并行查询历史价格、供应商履约和相似案例
→ 检索相关制度和处理规则
→ 生成结构化风险摘要
→ Review Agent 逐条检查证据
→ 如证据不足则打回补查或删除结论
→ 展示给楼长
→ 楼长自行决定通过、驳回或进一步核实
```

## 6. Human-in-the-loop

Agent 可以进一步生成：

- 通过意见草稿。
- 驳回意见草稿。
- 补充材料请求草稿。
- 采购分析报告草稿。

这些内容必须先由楼长或采购员检查和修改，确认后才能写入正式业务系统。

## 7. 关键要求

- Agent 只提供辅助分析，不替代审批决定。
- 每条风险必须有数据或制度依据。
- 供应商风险、价格异常等精确数值必须来自后端工具。
- Review Agent 必须能够查看工具结果和检索片段，而不是只看最终文字。
- 部分数据源不可用时，明确说明分析范围不完整。

# 九、采购填写流程

采购填写不作为核心 Agent 场景。

采购字段固定，使用表单比让 Agent 一轮一轮提问更高效。

推荐流程：

1. 用户直接打开采购表单，或先输入一段自然语言。
2. 模型从描述中提取可识别字段。
3. 系统将字段预填到完整表单。
4. 用户一次性补充和修改。
5. 后端执行必填校验。
6. 用户确认后正式提交。

该功能只是轻量入口能力，不设置独立重 Agent，不使用多轮对话逐项填写。

# 十、Agent 整体设计

第一版采用四个 Agent 或处理角色，不为了展示多 Agent 而继续拆分。

## 1. Router Agent

负责：

- 识别知识问答、复杂查询、审批调查和表单预填。
- 判断单任务或复合任务。
- 将复合任务拆成多个子任务。
- 选择后续工作流。

Router Agent 不负责生成复杂结论。

## 2. Knowledge Agent

负责：

- 采购制度、流程、角色职责和设备字段要求问答。
- 业务数据与规则结合解释。
- 返回带文档来源的答案。

主要使用 RAG 和少量业务查询工具。

## 3. Analysis Agent

负责：

- 自然语言复杂查询。
- 多约束候选方案。
- 审批风险补充调查。
- 多工具计划与执行。
- 跨数据源结果整合。

第一版不继续拆成查询 Agent、推荐 Agent 和风险 Agent。

## 4. Review Agent

负责：

- 检查事实是否有来源。
- 检查是否遗漏用户条件。
- 检查是否编造产品、价格、供应商或制度。
- 检查是否越过审批边界。
- 检查结论强度是否与证据匹配。
- 在发现问题时打回重查、重写或删除无依据结论。

Review Agent 需要同时读取：

- 用户原始问题。
- 路由结果。
- 查询计划。
- 工具调用记录。
- RAG 检索片段。
- 初步回答。

## 5. 表单预填模块

仅进行自然语言字段提取和表单预填，不作为独立重 Agent。

# 十一、统一处理链路

```text
用户输入
→ 后端校验身份、角色和数据权限
→ Router Agent 识别单任务或复合任务
→ 创建有状态工作流和 Trace ID
→ 加载对应 Skill
→ 生成结构化计划
→ Knowledge Agent 检索 RAG
→ Analysis Agent 通过标准 MCP 调用业务工具
→ 独立查询并行执行
→ 根据中间结果动态调整步骤
→ 生成结构化回答、对比结果或风险摘要
→ Review Agent 基于证据审查
→ 必要时打回补查或重生成
→ 高风险写入进入人工确认
→ 返回最终结果
→ 保存 Memory、Checkpoint、Trace 和评测数据
```

# 十二、知识库与数据要求

## 1. 知识库内容

- 采购流程说明。
- 各角色职责。
- 设备采购字段要求。
- 黑名单规则。
- 内部采购规范。
- 系统使用说明。
- 历史审核案例。
- 历史异常案例。

## 2. 文档管理要求

- 每份文档记录类型、适用角色、生效时间和版本。
- 支持文档更新和旧版本保留。
- 检索时按用户角色和权限过滤。
- 答案引用具体文档和片段。
- 过期文档不能作为默认依据。

## 3. 业务数据要求

至少需要：

- 采购申请。
- 审核记录。
- 历史价格。
- 产品白名单。
- 产品参数和兼容性。
- 供应商信息。
- 黑名单记录。
- 交付和延期记录。
- 入库记录。
- 风险检查结果。

# 十三、MCP 业务能力

需要实现标准 MCP Client 和 MCP Server，而不是只把普通函数命名为 MCP 工具。

## 1. 采购数据 MCP

- 查询采购申请。
- 查询历史采购。
- 查询审核记录。
- 查询采购状态。
- 查询入库记录。

## 2. 产品数据 MCP

- 查询白名单产品。
- 查询产品分类。
- 查询设备参数。
- 查询兼容性信息。
- 查询历史品牌和型号。

## 3. 供应商数据 MCP

- 查询供应商。
- 查询黑名单。
- 查询交付和延期记录。
- 查询历史合作情况。

## 4. 统计分析 MCP

- 计算历史平均价格。
- 检查重复申请。
- 检查异常数量。
- 统计品牌采购次数。
- 统计供应商履约情况。

## 5. MCP 调用要求

- Agent 作为 MCP Client。
- 业务能力通过 MCP Server 暴露。
- 工具参数使用固定 Schema。
- 查询工具默认只读。
- 工具级和数据级权限由 MCP Server 再次验证。
- 支持超时、重试、熔断和降级。
- 每次调用传递 Trace ID。
- 工具失败时返回明确错误，不允许 Agent 猜测结果。

# 十四、状态、记忆与恢复

## 1. 会话记忆

保存：

- 当前设备类型。
- 当前时间范围。
- 当前楼宇。
- 当前比较品牌。
- 已排除供应商。
- 已使用筛选条件。

## 2. 任务状态

保存：

- 当前查询计划。
- 已执行步骤。
- 已获得的数据。
- 待完成步骤。
- 查询结果摘要。
- 用户对结果的修正。

## 3. Checkpoint

复杂任务执行过程中保存检查点，支持：

- 工具或模型调用失败后恢复。
- 人工确认后继续执行。
- 用户中断后继续任务。
- 避免重复执行已经成功的步骤。

第一版不做复杂长期用户画像。

# 十五、领域能力封装（独立 Skills 为后续扩展）

以下 Skill 名称保留为领域规则分组，不表示当前存在独立 Skill Loader 或动态版本系统。

## Knowledge Skill

- 回答制度问题必须引用知识库。
- 文档没有依据时不得编造。
- 涉及具体采购单时必须调用业务工具。
- 文档冲突时提示版本差异。

## Query Skill

- 不得直接执行任意 SQL。
- 只能调用允许的只读工具。
- 查询结果必须保留筛选条件。
- 条件不足时最多进行一次必要澄清。

## Recommendation Skill

- 产品和供应商必须来自工具结果。
- 必须说明每个方案满足和不满足的条件。
- 不得声称存在唯一最优方案。

## Risk Skill

- 区分事实、规则命中、推测和信息不足。
- 不得替楼长完成审批。
- 每项风险必须对应具体记录或规则。

## Review Skill

- 检查来源、遗漏、越权和编造。
- 证据不足时打回，不直接放行。
- 重要结论必须能够追溯到工具结果或文档片段。

当前实现由结构化 Role Prompt、Tool Contract、Graph 节点、知识文档和 Backend 规则承载；独立动态加载属于 P1/后续扩展。

---

# 十六、结构化输出要求

以下内容必须使用固定结构：

- 路由结果。
- 子任务列表。
- 查询条件。
- 查询计划。
- 工具参数。
- 候选方案。
- 风险项。
- 证据来源。
- Review 结果。
- 最终报告。

结构化输出用于：

- 参数校验。
- 前端展示。
- 自动评测。
- Trace。
- 失败重试。
- 工作流恢复。

---

# 十七、权限与安全要求

- 身份、角色和楼宇权限由后端校验。
- Agent 不能依靠 Prompt 自行判断权限。
- MCP Server 必须再次进行工具级和数据级权限校验。
- 数据查询使用只读账号或只读工具。
- 正式写入必须经过人工确认。
- 知识库按角色和文档权限过滤。
- 敏感字段按角色脱敏。
- 防止用户通过 Prompt 诱导 Agent 获取越权数据。
- 所有工具调用和人工确认写入审计日志。
- Agent 不得把不完整分析描述为完整结论。

---

# 十八、稳定性与容错要求

- 模型输出 Schema 校验失败时允许有限次数重试。
- 工具调用支持超时和指数退避重试。
- 连续失败达到阈值后触发熔断。
- 主模型不可用时可以切换备用模型。
- RAG 不可用时明确降级为仅业务数据回答。
- 部分工具失败时只输出已确认范围，并说明缺失数据。
- 工作流设置最大步骤数和最大循环次数。
- 使用 Checkpoint 避免失败后从头执行。
- 相互独立的查询可以并行执行。
- 并行任务允许部分成功，并保留失败原因。

---

# 十九、Trace 与可观测性

每次请求生成唯一 Trace ID，记录：

- 用户输入。
- 用户角色和权限范围。
- 路由结果。
- 加载的 Skill。
- 查询计划。
- RAG 召回片段和得分。
- 工具名称、参数、结果和错误。
- 每一步耗时。
- 模型、Token 和估算费用。
- Planner 步骤数。
- Review 是否打回及原因。
- 最终是否完成任务。
- 用户反馈。

项目需要提供简单的执行详情页面或日志视图，能够展示：

```text
用户问题
→ 路由
→ 计划
→ RAG 与工具调用
→ 中间结果
→ 初稿
→ Review
→ 最终结果
```

# 二十、自动评测要求

## 1. Router 评测

- 单任务分类准确率。
- 复合任务识别率。
- 子任务拆分正确率。

## 2. RAG 评测

- 正确文档是否进入 Top-K。
- 引用是否正确。
- 回答是否忠于文档。
- 是否错误使用过期规则。

## 3. Tool 评测

- 工具选择准确率。
- 参数提取准确率。
- 工具调用成功率。
- 是否调用了越权工具。

## 4. 复杂查询评测

- 查询条件完整率。
- 查询结果是否满足条件。
- 是否遗漏排除项、分组或统计要求。
- 连续追问是否正确保留上下文。

## 5. 风险摘要评测

- 风险召回率。
- 错误风险率。
- 证据覆盖率。
- 是否将推测写成事实。
- 是否越权给出审批决定。

## 6. 端到端评测

- 任务完成率。
- 平均延迟。
- 平均工具调用次数。
- 平均 Token 和费用。
- Review 打回率。
- 人工评分。
- 版本回归结果。

# 二十二、验收标准

## 1. 知识问答

- 能区分文档问题、实时数据问题和混合问题。
- 回答包含正确来源。
- 没有依据时不编造。
- 文档与实时业务数据可以组合解释。

## 2. 复杂查询

- 能正确提取跨时间、楼宇、设备、供应商和金额的复合条件。
- 能生成合理计划并选择正确工具。
- 能在连续追问中保留原有条件。
- 结果与后端直接查询结果一致。

## 3. 审批调查

- 能读取后端风险结果并补查相关证据。
- 每条风险都能追溯到数据或制度。
- 能区分事实、风险提示和信息不足。
- 不替代人工审批。

## 4. 工程能力

- 工具失败、模型失败和检索失败都有明确处理。
- 工作流可记录、可恢复、可评测。
- 权限控制不依赖模型。
- 每次请求具有完整 Trace。
- 核心链路可以通过 Docker Compose 一键启动。

# 二十四、最终项目说明

> 本项目首先以网页版形式，在现有数据中心采购业务系统基础上增加平台无关的智能协同 Agent，重点支持采购知识与业务问答、自然语言复杂查询与分析、审批辅助与异常调查。系统通过有状态工作流组织路由、规划、检索、工具调用、结果审查和人工确认，使用 RAG 检索采购制度、流程和历史案例，通过标准 MCP 接入采购、产品、供应商和统计分析能力，并使用 Redis 保存连续分析上下文与任务状态。所有候选方案和风险结论必须有真实数据或文档依据，正式审批、状态流转和业务写入仍由原有后端系统控制。
